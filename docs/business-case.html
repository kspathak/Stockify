Stockify is a personal software project to build an end-to-end stock intelligence platform. It will ingest live market prices, enrich them with sentiment signals derived from financial news and social media, and produce short-horizon directional price predictions using machine learning.

The platform is built on proven, industry-grade open-source technology already partially scaffolded (Spring Boot, Apache Kafka, Prometheus). The total infrastructure cost ranges from $0/month on a developer laptop to $35–60/month on a cloud server — a fraction of equivalent commercial data subscriptions ($300–2,000+/month).

Six business decisions need to be made before or during the build. These are documented in Section 10 with recommended options and the financial and operational impact of each choice.

⚡
Key caveat for any business use of predictions: academic research consistently shows that short-horizon stock price prediction accuracy rarely exceeds 55–58% on liquid markets. Stockify's prediction module is a signal tool, not a guaranteed edge. Any decision to act on outputs should be made with that baseline in mind.

Problem Statement & Opportunity

Why this project exists

The Problem

Retail investors and individual traders lack affordable access to the kind of real-time, multi-signal intelligence that institutional desks take for granted. Commercial platforms offering live data, news sentiment, and predictive analytics charge $300–$3,000+ per month per user. Free tools provide fragmented, delayed, or low-quality data with no aggregation layer.

Even for personal use — tracking a watchlist, understanding why a stock is moving, or stress-testing a thesis against social sentiment — there is no cohesive, self-owned toolchain that a software engineer can build, control, and extend.

The Opportunity

A combination of free and low-cost market data APIs, open-source time-series databases, and open-weight NLP models means this capability can now be self-built for near-zero marginal cost. Stockify captures this opportunity by assembling a production-grade pipeline that:

Risk Register

Business and operational risks with mitigations
Free API Tier Changes Medium Risk
Data providers (Finnhub, NewsAPI, Reddit) may tighten or monetise their free tiers. This has happened before (Twitter/X in 2023) and could remove a data source with no notice.
Mitigation: Build provider abstraction layer so any source is swappable. Maintain a list of 2 fallback providers per data type.
Prediction Accuracy Below Expectation High Risk
Stock price prediction is a hard, well-studied problem. It is likely that the first model version will only marginally beat a random baseline. Stakeholders may interpret this as project failure.
Mitigation: Set expectations explicitly (see Section 1 caveat). Frame the value as the pipeline and signal tooling, not accuracy alone.
Scope Creep into Live Trading High Risk
Once predictions are running, there will be pressure to connect the system to a brokerage and execute trades automatically. This introduces capital risk, regulatory considerations, and a completely different risk profile.
Mitigation: Automated trading is explicitly out of scope (BR constraints). Any future expansion requires a separate business case and risk review.
Maintenance Burden Over Time Medium Risk
APIs change, libraries deprecate, models drift. A platform like this requires ongoing attention — estimated 2–4 hours per week — which may compete with other priorities.
Mitigation: Modular architecture makes individual components maintainable in isolation. Observability alerts surface issues proactively.
Data Quality Issues Medium Risk
Free-tier market data can include bad ticks, stale prices, and gaps during low-liquidity periods. Feeding bad data into the model will produce unreliable predictions.
Mitigation: Implement an input validation layer in the ingestion pipeline. Flag anomalous ticks (price deviation >5% in <1 min) before storage.
Infrastructure Cost Overrun Low Risk
If deployed on AWS and services scale unexpectedly, monthly costs could exceed projections. AWS billing is notoriously difficult to predict without careful capacity planning.
Mitigation: Use Hetzner VPS (fixed price) not AWS for personal deployment. Set a hard AWS billing alert at $100/mo if AWS is ever used.

Assumptions & Constraints

What this plan depends on being true

Assumptions

  • Finnhub's free WebSocket tier (50 symbols, 60 req/min) will remain available in its current form throughout the build period.
  • The project is for personal and educational use only. Commercial redistribution of data or signals may require paid data licenses — this has not been assessed.
  • The developer (owner) will spend approximately 10–15 hours per week on the project during the active build phases.
  • Prediction accuracy is not expected to support financial decisions on its own. The platform is a monitoring and analysis tool, not a trading system.
  • The hardware available for local development has at least 8 GB RAM (16 GB recommended to run FinBERT + all Docker services simultaneously).
  • The watchlist will initially be limited to US equities traded on NYSE/NASDAQ. Extending to other exchanges requires additional data source evaluation.

D1 Which database will store time-series price data? Blocking — needed before Phase 2

The choice of database determines how price history is stored, how fast it can be queried, and how easy it is to maintain long-term. This is the most consequential technical decision with direct cost and operational implications.

★ REC
TimescaleDB (PostgreSQL extension)
Standard SQL query language. Automatic time-based data partitioning. Works with existing Spring JDBC code — no new libraries needed. Free open-source. Industry standard for time-series on PostgreSQL.
Cost: $0 self-hosted · $0 additional dev time
B
InfluxDB
Purpose-built time-series database with excellent performance. Different query language (InfluxQL/SQL hybrid) requires learning and new library integration in Spring.
Cost: $0 self-hosted · ~5–8 extra hours integration
C
Plain PostgreSQL
Simplest option, widely known. Requires manual table partitioning by time window which adds complexity and degrades query performance at scale (>1 year of tick data).
Cost: $0 · Works now but creates technical debt
Implication of delay: Cannot build Phase 2 (persistent storage) until resolved.

D3 Which NLP model will score sentiment? Needed before Phase 3

The sentiment scoring model determines how accurately news and social posts are classified as bearish, neutral, or bullish. There is a direct tradeoff between accuracy, cost, and hardware requirements.

★ REC
VADER (Phase 3) → FinBERT (Phase 4+)
Start with VADER: rule-based, instant, zero hardware requirements, ~65% accuracy. Graduate to FinBERT (finance-tuned deep learning model, ~87% accuracy) when the pipeline is stable. Both run locally at no cost.
Cost: $0 · VADER: <1ms/text · FinBERT: needs ≥4 GB RAM
B
FinBERT from day one
Skip VADER and start with the higher-accuracy model. Requires Docker container with ≥4 GB RAM allocation. Good choice if hardware is not a constraint.
Cost: $0 · Requires developer machine with ≥8 GB free RAM
C
LLM API (Claude / OpenAI)
Highest accuracy (~90%+), zero local hardware requirement. Introduces per-call API cost and an external dependency. Suitable only if call volume is low and accuracy is critical from the start.
Cost: ~$3–10/mo at low volume · API dependency risk
Implication of delay: Sentiment pipeline cannot be built without a scoring model chosen.

D6 What prediction horizon and target should the model use? Needed before Phase 4

The prediction target defines what the ML model is trained to do. Different horizons have different difficulty levels, different use cases, and require different evaluation methods. This choice also determines what constitutes a "correct" prediction.

★ REC
Binary direction over next 1 hour (Up / Down)
Simplest target: will the price be higher or lower in 1 hour? Easy to evaluate, clear baseline (50% random), and provides a tradeable signal. Excludes "neutral" to keep the problem binary.
Simplest evaluation · Most comparable to literature benchmarks
B
Three-class direction: Up / Neutral / Down (EOD)
End-of-day prediction with a neutral band. More realistic but harder to evaluate and models tend to over-predict "neutral." Useful if the goal is a daily morning signal.
More complex evaluation · Harder to show value at first
C
Percentage price change range
Predict the magnitude of movement, not just direction. Much harder problem (regression vs. classification), requires more data and more careful feature engineering. Not recommended for Phase 4.
Significantly more complex · Best deferred to Phase 5+
Implication of delay: ML features and training pipeline cannot be finalised.
